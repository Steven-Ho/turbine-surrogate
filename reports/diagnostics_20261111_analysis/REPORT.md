# diagnostics.zip 分析：GeoTransolver 几何查询与 CPU 范围

**结论：几何查询重算是 GeoTransolver 当前慢速的直接主因。CPU 对照没有显示扩大主线程亲和性范围到 8 个 CPU 的稳定收益；但这不是严格的 4/8 核 Slurm 硬配额对照。**

两项状态均 complete；仅分析现有数据与制图，没有在本机运行模型或 GPU 试验。

## GeoTransolver：已确认的瓶颈

| 场景 | 完整前向/反向秒数 | 查询索引秒数 | 查询占比 | 命中/失效次数 |
|---|---:|---:|---:|---|
| A_cold | 12.34744 | 11.51647 | 93.27% | 2/2 |
| A_same_value_clone | 0.05853 | 0.00084 | 1.44% | 4/0 |
| different_sample_1 | 11.57851 | 11.52469 | 99.54% | 2/2 |
| different_sample_2 | 11.58427 | 11.52900 | 99.52% | 2/2 |
| return_to_A | 11.58878 | 11.52012 | 99.41% | 2/2 |

不同样本/切回 A 的平均前向反向为 11.584 秒，其中查询占 99.49%。重复同一几何仅 0.05853 秒。
缓存命中/失效符合当前设计：相同值命中，换样本后失效；切回 A 仍失效，证明只保留最近一份几何。
样本 B/C 与 A 的最大归一化坐标差分别为 0.04842 和 0.03505，不应强行复用同一份邻居索引。
每个半径一次完整查询约 5.75 秒；两个半径在每次换样本时各重算一次，合计约 11.5 秒。模型同一步内其余两次调用命中，并未消除这两次昂贵重算。
单个 29773×256 块：cdist 约 0.0482 秒，topk 约 0.00168 秒；cdist 占两者约 96.6%。这支持全点对距离计算是主要算子瓶颈。
分块降低峰值内存，但每样本仍需遍历约 N² 个点对，无法靠增加块数或只增加 CPU 解决复杂度问题。
首次 A 还包含其他初始化成本；切回 A 的传输时间有一次 0.468 秒异常，但其前向反向仍主要耗在查询，不改变主要结论。

## CPU：当前测试结果

八个条件使用相同初始权重校验值、同一 GPU/32 个完整训练样本、相同顺序与 Adam/MSE/LR；各预热 10 步后计时 100 步，4/8 范围各重复两次。
最终 loss 在 0.0149679985–0.0149679994 间，说明各条件优化器更新结果数值一致。

| 主线程亲和性 CPU 数 | 数值线程数 | 模式 | 毫秒/步 | 相对 4 CPU 速度 |
|---:|---:|---|---:|---:|
| 4 | 4 | disk | 131.73 | 1.000× |
| 8 | 4 | disk | 136.43 | 0.966× |
| 4 | 4 | memory | 130.53 | 1.000× |
| 8 | 4 | memory | 126.80 | 1.029× |

扩大到 8 个 CPU：disk 约慢 3.6%，memory 约快 2.9%；没有跨模式一致的明显收益，memory 的两次重复范围重叠。不能把几个百分点当成稳定加速。
disk 模式数据阶段约 7 毫秒，完整步骤约 132–136 毫秒；预载内存后仍约 127–131 毫秒。文件读取/反序列化不是当前稳定步骤的主导耗时。
前向/反向/Adam/同步合计约 117–119 毫秒，约占总步骤时间 87–92%；此计时也包含 CPU 提交算子和等待，不等同于纯 GPU 计算利用率。

### CPU 对照的边界与脚本局限

1. 实际 Slurm 作业始终申请 8 CPU；子进程通过 sched_setaffinity(0, ...) 改变主线程范围到 4 或 8，并设置同样的 4 个数值线程。这不是两个不同 Slurm CPU 硬配额作业。
2. 4 CPU 标签条件的“进程 CPU 时间/墙钟时间”为约 4.35–4.63，超过 4，提示后台线程可能使用了更宽的 CPU 范围，或需核验平台 CPU 时间记账。记录只核验了主线程，未核验全部线程。
3. torch inter-op 线程池配置为 128，两个范围均如此。这是配置容量，不证明有 128 个线程实际同时运行；也不能仅凭此认定它是瓶颈。
4. 因而目前只能说：在本次固定 4 数值线程、同一 8 CPU Slurm 分配中，扩大主线程亲和性没有带来稳定收益。不能严格排除真实 CPU 配额/后台线程调度对原训练的影响。
5. 未测试数值线程从 4 提升到 8，未测试完整预处理、验证和检查点阶段。若继续核实，应使用 Slurm 资源约束的 4/8 CPU 步骤并记录全部线程 Cpus_allowed_list；再单独改变 inter-op/intra-op，避免混在一次实验里。

## 后续优先级

1. 优先优化 GeoTransolver 的查询：按真实样本/坐标内容预计算并持久化邻居索引，或使用空间索引，避免每个优化器步骤执行两次 O(N²) 距离遍历。
2. 可共用同一几何的距离/最近邻候选生成来减少两个半径的重复工作，但仅合并两个半径仍不足以解决大量重复距离计算。
3. 保留各样本坐标与半径/邻居数/补零规则，不能把全部几何强制当 A；优化后应做索引/前向/梯度与真实样本对照，再测完整训练吞吐。
4. 不优先为所有任务增加 CPU。若要更严格的 CPU 因果结论，先修正亲和性核验和硬配额对照设计。
5. 本压缩包没有 Graph_UNet 算子诊断，无法说明此前首批卡顿是否已解决。
