本分析未使用外部规格表，因此不判定达到厂商峰值的百分比。

## 结论

已测两张卡的显存带宽及 GEMM 性能高度一致，所有 18 项性能测试均通过脚本内的正确性检查。
没有观察到某张卡计算性能明显偏低。实际时钟、PCIe 代际/宽度、降频原因尚未采集，
不能确认是否满频或排除长时间热降频。双卡作业逐卡测试，不表示并行双卡训练能力。

复制缓冲区为 256 MiB，大于报告的 8 MiB L2，整块数据完全由 L2 容纳的解释不成立。
显存带宽按一次读取加一次写入计算（2×数据量），单份有效载荷复制速率约 682 GB/s；
不能把 1364 GB/s 当作 CPU/GPU 互传速度。
GEMM 为 4096×4096 方阵，设置 allow_tf32=False；预热5次，5批，每批20次，以批均延迟中位数计算。
FP32 约3.854 ms/次，半精度约0.508–0.516 ms/次。

同一双卡作业中，GPU1 对比 GPU0：显存带宽低0.013%，FP32低0.017%，
FP16高0.005%，BF16低0.094%，差异很小。GPU0跨作业半精度算力变化约1.3%–1.4%。
GPU1回传比GPU0低7.91%；可能涉及主机NUMA、PCIe路径或短时波动，本数据不能定位原因。
同次GPU1回传批均延迟为9.093–9.594 ms，也比矩阵计算更有波动。

复制全量校验通过；GEMM 8×8 子块与 CPU FP64 参考的相对误差：
FP32约1.0e-6–1.2e-6，FP16约1.9e-4–2.3e-4，BF16约1.5e-3–1.6e-3，
均在脚本阈值内。这是有限规模的算子检查，不是全显存可靠性认证。

## 监控的局限

单卡性能作业只有4条采样，双卡7条，只查询作业1条。性能作业样本温度37–49℃、
功耗91–142 W，功率上限450 W；这些是采到的值，不是完整运行峰值。
FP32主计时区间约0.385秒，半精度约0.051秒，每秒采样很容易错过，且管理工具
读数可能有刷新延迟。因此低 GPU-Util、低功耗不能说明算力测试未充分使用GPU，
也不能拿这些读数计算满载能效。

Perf显示P9/P0，但记录没有状态定义、MHz或降频原因，不能套用其他厂商的P状态解释。
这次脚本仅执行ht-smi默认输出，确实遗漏了用户希望核实的实际时钟频率。

## 下一步补测

归档中的ht-smi --help明确支持下列只读参数，可在已分配GPU的计算节点逐条执行：

```bash
ht-smi --show-clock
ht-smi --show-clocks all
ht-smi --show-dpm cur
ht-smi --show-pcie
ht-smi --show-hwinfo
ht-smi --show-ecc-state
ht-smi --count-ecc
ht-smi --show-clk-tr
```

最后一条帮助注明仅支持C类设备，若不适用需保留错误，不能解释为“无降频”。
时钟应在持续负载期间另行采样；仅空闲时查询不能核实负载频率。
可用原测试脚本增加迭代数，让每个阶段获得更多采样：

```bash
sbatch --gres=gpu:2 --time=00:30:00 scripts/slurm_gpu_probe.sh --iterations 1000 --repeats 5
```

该命令本身仍只采集默认ht-smi字段，需另行执行上述频率采样或扩展采集脚本。
随后对CPU绑定/NUMA分配一致的环境复测GPU→CPU，核实约8%的差异是否稳定。
多卡MarsLink/P2P、集合通信、跨节点网络、真实模型训练效率均不在本次覆盖范围内。

对turbine-surrogate的含义：数据支持两张卡具有一致的稠密计算及显存复制能力。
FP16/BF16 GEMM约为FP32的7.5倍，但端到端训练不能据此按7.5倍估算；
图邻域查询、散射聚合、小算子、数据准备等仍需实际模型剖析。
